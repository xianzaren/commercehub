# 商家仪表盘：架构、测试与 Bug 案例

## 底层架构

CommerceHub 是前后端分离的单体应用：Next.js / React 页面调用 FastAPI，身份依赖检查用户角色及商家状态，Service 确定业务口径和店铺归属，Repository 使用 SQLAlchemy 查询 MySQL。Alembic 管理表结构。金额在后端使用 Decimal，订单保存成交价格与商品名称快照，库存通过库存表和流水记录管理；当前 SKU 共享商品库存。

新增链路：`merchant-analytics.tsx` → `GET /api/merchant/analytics/dashboard` → `AnalyticsService` → `AnalyticsRepository` → `orders / payments / order_items / products`。图表用 React + SVG 绘制，无额外图表依赖。已有索引和表结构足够支持本次功能，未新增数据表。

## 使用仪表盘

打开 http://localhost:3000/login，使用演示商家 `merchant1@commercehub.example.com`、密码 `Demo1234!` 登录，进入“经营概览”或“经营分析”。

- 近 7 / 30 / 90 天与截止日期；可筛选全店或单个商品。
- 销售额、订单数、销售件数、客单金额及上个等长周期比较。
- 收入折线图、日销量柱状图、商品销量排行、低库存提醒。
- 鼠标或 Tab 查看逐日数值，也可展开每日数据表；点击刷新获取最新数据。
- 无交易时显示真实零值，不注入假交易来制造曲线。现有演示订单日期较集中，可调整截止日期查看。

## 统计口径

按 `payments.paid_at` 的北京时间自然日分组，区间为起点包含、终点不包含。只计成功支付且订单处于 PAID / PROCESSING / SHIPPED / COMPLETED 的交易，排除未支付、取消、退款记录。历史退款会使对应历史区间的有效销售额减少，本功能不是会计现金流报表，也不计算利润。

全店销售额来自订单总额，销量来自订单明细，分别聚合以避免多条明细重复放大订单金额。单商品筛选使用该商品的历史成交小计，不使用当前售价。排行按商品 ID 合并所有 SKU 和历史名称，以当前商品名称展示。零成交日期补零。统计店铺从登录商家推导，接口不接受客户端指定任意店铺。

日期区间不超过 90 天；今天未结束时，与上期整日区间的比较应视为阶段性结果。没有上期收入时不显示无穷增长率。图表手动刷新，不是实时推送。

## 一键运行

在项目根目录运行（Docker Desktop 需启动）：

```powershell
.\scripts\test-merchant-analytics.ps1
.\scripts\test-merchant-analytics.ps1 -Mode All
```

脚本返回非零退出结果表示失败。测试会重建配置中的 `*_test` 数据库，fixture 拒绝没有 `_test` 后缀的库；入口直接执行 pytest，让保护检查发生在迁移之前。不要将真实业务数据库命名为测试库或将测试连接配置指向真实业务数据。

也可只运行某个案例：

```powershell
docker compose --profile test run --rm --entrypoint pytest backend-test -q tests/integration/test_merchant_analytics.py -k bug_001
```

## 已实际复现并修复的 Bug

| 编号 | 构造数据 | 修复前结果 | 正确结果 / 回归用例 |
| --- | --- | --- | --- |
| BUG-001 | 1 月 1 日下单 ¥100，1 月 2 日付款 | 1 月 1 日收入 ¥100 | 1 日为 0、2 日为 ¥100；`test_bug_001_revenue_uses_payment_time` |
| BUG-002 | 同一个商品以旧名称卖 2 件，改名后卖 1 件 | 排行拆成两行，数量 2 和 1 | 一行 3 件、¥150；`test_bug_002_product_rename_must_not_split_ranking` |
| TEST-003 | 在旧搜索测试之前新增其他测试商品 | “Mechanical”字符匹配多个商品，旧用例硬断言只有 1 件而失败 | 查询限定该用例独立分类，消除跨用例数据干扰 |

BUG-001、BUG-002 在修改实现之前分别得到 `100.00 != 0`、`len(rows) == 2 != 1` 的真实失败。修复后同一用例必须通过。保留用例和上述错误输出，便于学习；不要把缺陷重新注入运行中的应用。

## 额外防回归场景

- UTC 16:00 应归入北京时间次日，区间尾端不重复计入。
- 一个订单包含两种商品：总额 ¥110，只计一次；数量为 3 件。
- 筛选单个商品：只计对应 ¥100 和 2 件。
- 空日期连续补零；上期 ¥100、本期 0 正确返回。
- 一次失败支付加一次成功支付，只计一个订单；退款后排除。
- 商家不能读取其他店铺商品统计；访客 401、顾客 403。
- 无效天数、日期、商品编号拒绝；未来截止日期拒绝。
- 今日摘要采用北京时间，与趋势图一致。

## 前端人工验收

1. 商家登录，确认初次加载后四个指标和两张趋势图出现。
2. 切换 7/30/90 天，展开明细确认对应行数；快速切换检查旧请求不会覆盖新筛选。
3. 选择单商品，核对图表销量、排行和订单成交小计。
4. 切换无成交日期，确认显示零数据而非错误或虚构成交。
5. Tab 聚焦图表日期，确认读数变化；缩小窗口检查图表和筛选控件换行。
6. 断开后端再刷新，确认出现错误提示，不显示旧数据冒充新结果；恢复后点击刷新。
